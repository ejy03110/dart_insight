# F2001 메타데이터 수집·저장

관련 기준: 원본 PDF p.11의 F2001, `requirements-analysis.md` F2001 행.
구현 코드는 완성했지만 Codex에서 실제 API 데이터 100건 확보는 **미검증**이다.
사용자가 확인한 삼성전자 2025년 정기공시 4건은 연결 성공 사례이며, 세 기업 100건 증빙과 구별한다.

## 변경 범위

- `dart_insight/data/collection.py`: 기존 `DartClient.resolve_company()`로 공식 기업코드에서
  세 종목을 식별한다. 기업·유형별 `list_disclosures(max_pages=None)`로 전체 페이지를 조회한다.
  `Disclosure`와 `to_index_text()`를 재사용하며 접수번호로 중복 제거한다.
- `dart_insight/collect.py`: 수집·저장·집계 전용 CLI. 기존 연결 확인 CLI는 유지한다.
- 기존 `DartClient`, `Company`, `Disclosure`, `JsonCache`, 호출 간격·재시도·TTL 설정은 변경하지 않았다.
- F2002 임베딩/벡터 DB, 원문 다운로드, RAG는 구현하지 않았다.

## 실제 수집 명령

저장소 루트에서 기존 가상환경을 활성화하고 `DART_API_KEY`를 환경변수나 `.env`로 설정한다.
키를 명령 인자·로그·채팅에 넣지 않는다. CLI는 Streamlit Secrets 파일을 직접 읽지 않는다.

```bash
cd /workspace/dart_insight
source .venv/bin/activate

# 권장: A~J 전체 유형, 모든 페이지. API 직접 검증 시 캐시 우회
python -m dart_insight.collect --begin 2025-01-01 --end 2025-12-31 --refresh

# 정기공시만 선택: 100건 미달 시 과거 1년 구간씩 확대
python -m dart_insight.collect --begin 2025-01-01 --end 2025-12-31 --types A --earliest 2015-01-01

# 여러 유형 선택·저장 상위 경로 지정(기존 실행별 결과는 보존)
python -m dart_insight.collect --begin 2025-01-01 --end 2025-12-31 --types A B I --output-dir .local/data/metadata
```

기본 유형은 A~J, 목표 고유 건수는 100이다. `--minimum-count`로 100 이상을 지정할 수 있다.
기본 기간 확대 하한은 2000-01-01이며 `--earliest`는 최초 `--begin`보다 늦을 수 없다.
조회 종료일은 고정하고 최초 범위보다 이전의 1년 구간씩 추가한다.
예: 2025-01-01~2025-12-31 → 추가 2024-01-01~2024-12-31.
각 구간에서 세 기업·모든 선택 유형·모든 페이지를 마친 뒤 목표를 검사한다.
중간에 100건을 넘었다고 나머지 기업/유형/페이지를 생략하지 않는다.
자료가 없는 기업이 있으면 총합이 100 이상이어도 기간을 더 확대한다.
기간 확대는 과거 방향이며, 하한까지 부족하면 유형·하한·최초 범위를 사용자가 재설정해야 한다.
`--types A`만 선택하면 많은 연도를 조회할 수 있으므로 호출량·일일 한도에 유의한다.

`--refresh`가 없으면 기존 TTL 캐시를 사용한다. 응답의 `collected_at`은 원래 수집시각을 유지한다.
`--refresh`는 목록 캐시를 우회하고 기업코드도 첫 기업 식별 시 갱신한다.
기본 기업코드 TTL에서 같은 실행의 이후 기업은 갱신된 캐시를 재사용한다.
로그에는 기업·유형·기간만 출력하며 키·요청 전체 URL·traceback은 출력하지 않는다.

## 종료 코드·실패 처리

| 종료 코드 | 의미 | 저장 |
|---|---|---|
| 0 | 모든 조회 완료, 고유 공시 ≥ 목표(최소 100), 세 기업 모두 1건 이상 | `status=complete` 결과 |
| 2 | 하한까지 조회했지만 총합 또는 특정 기업 자료 부족 | 실제 받은 자료만 `status=insufficient_data`로 저장 |
| 1 | 인증·한도·통신·설정·저장 오류 | 성공 결과 생성하지 않음. 기존 실행 결과는 보존 |

인자 형식 오류도 argparse에서 종료 코드 2를 사용한다. 이 경우에는 수집 결과 파일이 없다.
013은 정상 빈 조회이며 과거 구간 확대 판단에 사용한다. 인증/일일 한도/통신 실패는 빈 결과로 바꾸지 않는다.
중간 API 실패 시 이번 집계 JSON은 저장하지 않지만, 이전에 받은 성공 응답의 기존 캐시는 남을 수 있다.
예전 `complete` 파일이 있어도 이번 실패 실행의 성공 증빙으로 간주하지 않는다.

## 저장 형식·검증

기본 위치: `DART_DATA_DIR/metadata/run-<실행별 고유 이름>/collection.json`.
`DART_DATA_DIR` 기본값은 저장소의 `.local/data`이며 Git에서 제외된다.
매번 새 실행 폴더에 임시파일을 작성하고 원자적으로 교체해 이전 결과를 덮어쓰지 않는다.

- `schema_version`, `requirement`: 저장 형식 버전과 F2001 표시.
- `summary.status`, `minimum_count`, `total_unique_count`, `company_counts`: 성공 조건·전체/기업별 집계.
- `summary.companies`: 사용자용 기업명과 공식 기업명·종목코드·기업코드 연결.
- `requested_period`: 최초 요청 범위. `queried_period`: 실제 완료한 전체 조회 범위.
- `queried_windows`: 중복 없는 조회 구간들. `queries`: 기업·유형·구간별 반환 고유 건수.
  유형별 건수를 합하면 중복 때문에 최종 고유 건수보다 클 수 있다.
- `sample_index_text`: 공시 한 건의 색인 텍스트. 빈 결과면 null.
- `disclosures`: 접수번호당 하나의 정규화 메타데이터와 `index_text`.
  기업명·공시명·접수번호·접수일·공시 유형·원문 URL을 포함한다.
  여러 유형에 걸친 공시는 `disclosure_type`에 조회된 유형 이름들을 합쳐 보존한다.

CLI는 진행을 stderr에, 저장 경로와 전체 요약 JSON을 stdout에 출력한다.
stdout의 `output_path`로 저장 파일을 찾아 다음처럼 예시 텍스트와 건수를 재확인할 수 있다.

```bash
# collection.json 경로는 실제 output_path 값으로 교체
python -c 'import json,sys; d=json.load(open(sys.argv[1],encoding="utf-8")); print(d["summary"]["company_counts"]); print(len(d["disclosures"])); print(d["summary"]["sample_index_text"])' .local/data/metadata/run-실제이름/collection.json
```

실제 검증 시 보관할 증빙: 명령·종료 코드, summary, 저장 JSON, 고유 접수번호 ≥100,
기업별 자료 존재, 실제 조회 기간, 한 건의 색인 텍스트. 파일에 키가 없는지도 확인한다.
이 파일은 **색인 입력 데이터**이며 ChromaDB 색인 완료나 F2002 검증 증거는 아니다.
