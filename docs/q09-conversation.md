# Q-09 멀티턴·응답 정책·본문 채팅 입력창

## 확인한 원인과 구현

기존 `histories[rcept_no]`에는 성공한 사용자/AI 쌍이 저장됐지만 실제 GMS 호출에는 현재 질문과 evidence만 들어갔다.
`RagService.ask`와 LangGraph/GMS JSON payload에 최근 대화를 연결했다. 새 질문이 저장되기 전 기록의 복사본을 전달한다.
대화는 본문 챗봇의 같은 공시 bucket에서만 가져오며, 새 turn에는 rcept_no도 표시한다.
다른 공시로 이동하면 별도 bucket을 사용하고, 돌아오면 같은 브라우저 세션의 기록을 다시 표시한다.
기존 자동 핵심 분석은 analyses에 유지하며 대화 기록에 끼워 넣거나 추가 질문 때 재실행하지 않는다.

전달 범위는 **최근 최대 6턴(사용자/AI 12메시지), 본문 합계 12,000자**다.
오래된 쌍부터 제외하며 답변·목록 중간을 자르지 않는다. 최신 쌍 자체가 예산보다 크면 과거 답변을 대신 전달하지 않는다.
이 제한은 정확한 모델 토큰 계산이 아닌 문자 예산이다. 현재 공시 evidence를 대화 때문에 자르는 코드는 추가하지 않았다.
질문별 문맥 해시로 기존 SQLite 검색/선별 캐시를 구분하되 대화 transcript/AI 답변 전체는 DB에 저장하지 않는다.
원래부터 저장하던 현재 질문·검색어·선별 원장과 공시 본문은 유지한다. 브라우저 종료 후 대화를 복원하는 영구 저장은 추가하지 않았다.

검색어 추출에는 역할 순서가 있는 최근 대화가, 후보 선별에는 사용자 질문 문맥이 전달된다.
대명사 질문의 벡터 검색에는 사용자 의도와 이전 설명의 주제를 **미검증 검색 문맥**으로만 붙인다.
이전 설명은 청크로 색인하거나 evidence에 추가하지 않는다. 실제 RAG 검색 결과만 현재 근거 번호를 받는다.
최종 GMS payload는 question/history/response_style/evidence이며 기존 출력 스키마 answer+supported는 동일하다.
과거 답변의 [근거 N]은 현재 번호가 아니므로 그대로 인용하지 말라는 정책을 명시했다.

## 이전 항목 회상과 새 사실의 구분

“방금 말한 세 번째 이유가 뭐였지?”처럼 명시적인 이전 항목 회상은 마지막 AI 답변의 실제 목록에서 찾는다.
순차 숫자/Markdown 번호·제목, 명확한 단일 글머리 목록, 첫째/둘째/셋째 순서를 지원한다.
번호가 반복되거나 순서가 불명확하고 지원되는 단일 목록을 식별하지 못하면 확인 요청을 반환한다. 이전 대화가 없으면 내용을 만들지 않는다.
“앞서 말한 세 번째 이유가 사실인지 근거로 검증해줘”는 회상 경로가 아니라 실제 RAG로 보낸다.

순수 회상은 원래 항목의 표현을 인용한 한 문장으로 답하고 예전 근거 번호를 제거한다.
예: `이전 답변에서는 세 번째 이유로 “…”라고 설명했습니다.`
새 금융 사실을 주장하는 답변이 아니므로 공시 인용을 생성하지 않는다. audit.answer_basis=conversation과
화면의 ‘이전 대화에서 확인한 내용’ 표시로 구분한다. 이 경로는 다운로드/임베딩/LLM을 재실행하지 않는다.
이것은 근거 부족 금융 질문의 fallback이 아니다. 새 사실 질문의 스키마·supported·인용 범위·근거 부족 검증은 그대로 유지한다.

## 말투와 형식 정책

문장 끝 문자열 치환 없이 공통 답변 프롬프트를 수정했다. 자연스럽고 전문적인 ~습니다/~입니다 체를 요구한다.
원문 직접 인용·회사명·법률 용어는 임의로 바꾸지 않는다.

| response_style | 적용 |
|---|---|
| analysis | 핵심 분석 버튼: 기존 핵심 요약/명시된 위험/추가 확인 보고서 |
| detailed | 명시적인 상세 분석: 제목·목록·근거 |
| one_sentence | 한 문장/한 줄 요청: 제목 없이 직접 한 문장 |
| brief | 짧게/간단히: 1~2문장 |
| easy | 쉽게 설명: 제목·반복 결론 없이 쉬운 2~4문장 |
| conversational | 일반 질문: 필요한 만큼 간결하게 직접 답변 |

‘사업보고서’라는 공시명만으로 상세 모드를 선택하지 않으며 명시적인 짧은 답변 요청을 우선한다.
말투·분량은 생성 정책이며 기계적으로 문장 수/종결어를 강제 변환하지 않는다.
실제 GMS의 설명 품질과 정책 준수는 Windows 실검증이 필요하다.
기존 인용 검증은 형식·번호·실제 청크 ID 매핑을 보장하며 모든 문장의 의미적 함의를 자동 입증하는 장치는 아니다.
과거 AI 답변이 새 증거가 되지 않도록 입력/검색/evidence 경로를 분리했지만 실제 모델의 주장 적합성도 확인해야 한다.

## 본문 채팅 UI

문제는 새 메시지를 chat_input 뒤에 바로 렌더링한 것이었다.
성공 시 save_turn 후 rerun하여 항상 전체 메시지를 먼저, 단일 입력창을 마지막에 렌더링한다.
기본 Streamlit 1.62.0의 `st.container(height=450, autoscroll=True)` 안에 시간순 대화를 표시하고
입력창은 그 컨테이너 바로 아래에 둔다. 높이가 고정돼 대화가 길어져도 입력창 위치가 계속 밀리지 않는다.
커스텀 JavaScript/CSS 스크롤 가로채기는 없다. 핵심 분석 영역과 기존 탭 UI는 변경하지 않는다.

- 실제 GMS 클라이언트가 보내는 JSON 요청에서 history 역할·순서와 현재 evidence가 별개임을 확인.
- 실제 임시 Chroma/SQLite/LangGraph에서 첫 상세 답변→두 번째 쉬운 설명→세 번째 실제 항목 회상,
  한 문장 요청·공시 격리·없는 대화 안내·잘못된 인용 거절·SQLite에 세션 전용 AI 문구 미저장을 검증.
  외부 HTTP/LLM/BGE는 Mock/테스트 구현이다. 회상 문장·금융 내용 fixture를 실제 모델 품질 검증으로 보지 않는다.
- AppTest: 공시 변경/복귀, 분석 유지, 현재 질문 중복 전달 없음, 입력창 1개, rerun 중복 실행 없음, native autoscroll 설정.
- Linux Chromium 154 실제 브라우저, UI만 Mock 서비스로 주입: 기존 30메시지에 연속 두 질문 후 32→34메시지,
  입력창 1개이며 DOM상 마지막 메시지 뒤/대화 컨테이너 아래, 자동 스크롤 하단 오차 2px 확인.
  입력창 y좌표가 두 질문 후에도 동일했다. Playwright는 기존 /tmp 별도 환경만 사용했고 제품 의존성은 바꾸지 않았다.
- GMS 키 미설정 확인. 실제 GMS 응답·Windows Python 3.11/브라우저·실제 BGE 추론은 이번 작업에서 미검증.

## Windows 재검증

```powershell
git pull --ff-only origin feat/required-rag-integration
$env:PYTHONUTF8 = "1"
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m streamlit run app.py
```

1. 실제 유상증자 공시에서 첫 질문을 하고 두 번째는 ‘그럼 왜 그런지 쉽게 설명해줘’로 질문한다.
2. 직전 답변의 목록을 확인한 뒤 ‘방금 말한 세 번째 이유가 뭐였지? 한 문장으로만 답해줘’라고 묻는다.
   화면에 보인 직전 항목의 실제 표현이 인용되는지, 대화 출처 표시가 있는지 확인한다.
3. ‘그 이유가 실제 공시에 있는지 근거로 확인해줘’는 새 공시 검색·현재 근거 검증을 거치는지 확인한다.
4. 빈 대화의 다른 공시에서 이전 항목을 물으면 확인 요청이 나오는지 확인한다. 돌아오면 원래 기록이 복원돼야 한다.
5. 긴 대화에서 연속 질문한다. 최신 메시지로 자동 스크롤되고 입력창이 대화 아래 하나만 있는지 확인한다.
6. 상세 요청/쉬운 요청/한 문장 요청과 핵심 분석 버튼의 형식, ~습니다 체, 직접 인용 보존을 확인한다.
   모호한 목록은 임의로 고르지 않고 항목 지정을 요청하는 것이 정상이다.

기존 .env/Chroma/SQLite 데이터를 삭제하거나 덮어쓰지 않는다. master 병합/실제 배포/고급 기능 추가 없음.
